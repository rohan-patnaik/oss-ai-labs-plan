0. TL;DR

The pattern behind nearly every recent external merge is: find a bug yourself, file a precise issue, open the small tested PR within the hour. Speed on fresh issues beats waiting for labels.

3b. When a repo has no free bugs: source your own issue

The tier-1 repos with the fastest merges (OpenAI Agents SDKs, claude-code-action, adk-python, markitdown, NeMo Agent Toolkit, OpenHands) are also the ones where every triaged bug gets a PR within hours. For those, the reliable path is to bring the issue yourself: find a real complaint, reproduce it, file it with a minimal repro, then open the fix. The reporter of a bug is the natural owner of its PR, and maintainers treat it that way (peft, OpenAI, Google and Microsoft repos all showed this pattern).

The loop

  1. Harvest complaints from the places users actually go (per-repo list on the right). Look for "hangs", "silently", "wrong", "ignored", "after upgrade", "only on Windows / macOS", "with subagents / async / streaming".
  2. Cross-check the tracker for an existing issue or PR: gh issue list --repo X --search "keywords" --state all and gh pr list --search. If it exists and is unowned, that is your issue. If it has a stale PR, review it instead.
  3. Reproduce against the current main branch with a script under 40 lines. Record versions, OS, exact command, expected vs actual output.
  4. File the issue with the repro, the root cause if you found it, and one sentence on the fix you intend. Link the forum thread. Use the repo's bug template exactly.
  5. If reproduction fails but the report is plausible, still file it as a question-style bug with what you tried and ask for the reporter's environment. That earns triage credit and often surfaces the real repro.
  6. Open the PR within the hour, Fixes #N, regression test included, forum thread quoted in the PR body as user impact.

Where complaints live, per repo

  • openai-agents-python / -js: OpenAI Developer Community, Bugs category. Live threads today: MaxTurns exceeded / "model did not produce a final response", handoff loop and MCP bypass. Check which parts are SDK-side, not API-side.
  • claude-agent-sdk-python / claude-code-action: downstream projects' trackers surface SDK bugs first, e.g. Aperant #762 orphaned processes (upstream is #434) and omnigent #575 subagent respawn. Also the Claude Developers Discord and anthropics/claude-code issues that mention "SDK".
  • adk-python / adk-go: adk-python Discussions Q&A and adk-go Discussions. Many "how do I" threads are unfiled bugs. r/googlecloud and Stack Overflow tag google-adk.
  • MCP go-sdk: third-party module reviews such as gh-aw-mcpg #12637 list concrete defects (nil-params panic became #1261). Also the org Discussions.
  • peft / huggingface_hub: HF forums. Recurring: multi-GPU + quantization + LoRA combinations, FSDP + gradient accumulation errors, eval loop skipped with PEFT models. Each is a candidate repro.
  • markitdown: almost no forum chatter. Build your own corpus: odd DOCX numbering, RTL PDFs, RSS with repeated slashes, one-byte outputs. The maintainer files these himself (#2468); you can too.
  • OpenHands / hermes-agent: Discord bug channels and Reddit r/LocalLLaMA; the issue trackers already convert these quickly, so speed matters more than sourcing.
  • X / Twitter: not indexable by search; use it only by following the maintainers listed in section 2 and watching replies to release posts.

4. How to maximize merge probability

Before writing code

  1. Only resolve filed issues. Every PR fixes a bug or a real user-reported problem with an issue number, or an issue you filed with a repro. No docs, typo, cookbook, notebook or "improvement" PRs; they do not count as engineering signal and they fall under maintainers' radar.
  2. Read CONTRIBUTING.md, AGENTS.md / CLAUDE.md, the PR template, and .github/workflows for CLA/DCO bots. Your osv-scanner PRs died on this alone.
  3. Check for generated code: grep -rl "DO NOT EDIT\|stainless\|fern\|speakeasy", .stats.yml, .castiron-ratchet.json. playwright-python #3085 died here.
  4. Check the issue timeline for cross-referenced PRs and the open PR list for the same title. If one exists, review it or move on.
  5. Comment a one-paragraph plan and wait for a maintainer nod on anything that changes behaviour. Respect hard gates (goose Ready, python-sdk assignment, gemini-cli approval, cline approval).
  6. Sign the CLA (Google, Meta, Microsoft, EleutherAI) or set up DCO + SSH signing (vLLM, NVIDIA, dynamo) before the first push so the bot check is green.

Writing the PR

  1. One PR per repo at a time. Never batch three into a new repo the same day.
  2. Keep it small. Your merged PRs were +4 to +149 lines; sampled external merges in agents-js were 1–5 files.
  3. Run the real test suite locally and paste the command and result in the PR body. playwright #40994 was closed because it was never run.
  4. Add a regression test in the same PR.
  5. Follow conventions exactly: conventional commits, bracketed titles (vLLM), changesets (agents-js), CHANGELOG (OLMo-core), Go style + commit format (go-sdk).
  6. Disclose AI assistance where required (MCP org, vLLM Co-authored-by) and make sure the code reads as hand-verified.
  7. Link the issue with Fixes #N and describe verification steps, not just the diff.

After opening

  1. Fix red CI within hours. playwright-python #3099 was superseded while waiting.
  2. Respond to reviews the same day and keep the branch rebased.
  3. Nudge once after the repo's median merge time passes, tagging whoever merged the last three external PRs. Never twice.
  4. Do not open a competing PR on an issue that already has one. Review the existing PR instead; that also builds a footprint.

Portfolio level

  1. Prefer maintainer-filed issues (markitdown #2468, unsloth-zoo #1251, OLMo-core #849, qwen-code #12002, delphi #38, hub #1756). The person who wants the fix is the person who merges.
  2. Self-source bugs: run the SDK against edge cases, file a precise issue with a repro, open the fix within the hour. This is the dominant merged pattern at OpenAI, Anthropic, Google, Microsoft, NVIDIA and OpenHands.
  3. Watch issue feeds twice a day: gh issue list --repo X --search "sort:created-desc no:assignee". Unassigned bugs get PRs within 1–3 days.
  4. Keep a "Merged upstream" list in your profile README, linking each PR, grouped by lab. That is the artefact a recruiter opens.
